# Korean hard set — 2026-09-08

Program §28: *clean Hangul, scanned Korean, Korean/English mixed, finance, Office
Korean fonts, PPTX/DOCX/XLSX, HWPX where supported, screenshots/photos. No
multilingual claim from English benchmarks alone.*

This directory is the fixture family for that section. It is **not** a benchmark
and it publishes no accuracy number. It is seven real Office packages, two
rendered pages, and a manifest that says for every §28 family whether the
coverage is real, synthetic or absent.

Everything here is generated by `build_korean_hard_set.py` from literals in that
file, so the expected values are what the builder wrote and never what a parser
reported back. `tests/unit/test_korean_hard_set.py` re-runs the builder and
asserts the committed bytes.

## What the rendered pages are, and are not

`rendered/korean-page-clean.png` is a page this builder **drew** with Pillow,
using `apps/web/public/fonts/wanted-sans-ko-400.woff2` — a font already
committed to this repository under the SIL Open Font License. No proprietary
font is read, rendered or committed.

`rendered/korean-page-SYNTHETIC_DEGRADATION.png` is that page after a fixed
1.4° rotation, a fixed 1.1 px Gaussian blur and a fixed contrast reduction.

It is **not a scan.** A real scan carries paper texture, a real scanner's
optics, a real printer's halftone, skew that varies down the page, and a
compression history. None of that is simulated. It is **not a photograph**: no
camera, no screen, no device. Its value is that its ground truth is known
exactly — the five lines are in `renderedPages[*].groundTruthLines` — so the OCR
lane can measure against it. This lane measures nothing against it and
`measured` is `false` in the manifest.

Nothing in this repository may cite these pages as evidence of scanned-Korean
performance.

## HWPX — `NOT_SUPPORTED`, zero code

There are no HWPX matches anywhere in this repository, and nothing here is a
stub for one. `/api/v1/capabilities` does not list HWPX, and it must stay off
every public "supported" list until all of the following exist:

1. **A reader provider.** `python-hwpx` is the standing candidate
   (`USKC_FOUNDER_DECISIONS_RESOLVED_2026-09-06.md`); its licence, its
   maintenance and its behaviour on a malformed package are unexamined. Legacy
   HWP v5 is a different format again and is excluded from initial production
   support (`REVIEW_REQUIRED`).
2. **An EvidenceLocator v2 variant.** The frozen schema has `docx`, `xlsx`,
   `pptx` and ten others, and no HWPX. An HWPX unit would have nothing to be
   addressed by, exactly as an endnote does not today. That is an enums v2
   change, which no agent may make.
3. **A `SourceFamily`, a MIME allowlist entry and the security preflight.** HWPX
   is a ZIP container, so it needs the same archive-entry, ratio, external
   relationship and embedded-object rules the OOXML path has.
4. **A corpus.** Same shape as this one: real files, literals, a receipt.

Until then the honest status is `NOT_SUPPORTED`, and this file is the reason.

## Reproducing

```
python research/korean_hard_set_20260908/build_korean_hard_set.py
python tools/office/qualify_office_readers.py \
    --corpus-root research/korean_hard_set_20260908 \
    --receipt-stem korean_hard_set_qualification
pytest tests/unit/test_korean_hard_set.py
```

The receipts land in `docs/evidence/receipts/` and every one of them is
`BEST_EFFORT`. Founder ruling G-6 needs six kinds of evidence for
`VERIFIED_NATIVE`; this tool can produce four, and the Korean set does not
change that arithmetic.

# H1-E — identity matching scalability: root cause, shadow policy, equivalence

Frozen 2026-08-19, **before** any equivalence or scaling number was produced
under `MatchingPolicy.BLOCKED`.

This protocol governs one question and no others:

> Can the semantic-identity matching stage be made to scale without changing a
> single identity decision, and where exactly does that guarantee stop?

It does **not** re-open the Family B fresh-seed holdout
(`receipts/final-fresh-holdout-2026-08-19.json`, sealed, one-shot, primary
success true). Nothing here may re-tune, re-run or re-interpret it.

---

## 1. The measured problem this starts from

`receipts/measured-performance-v2-2026-08-19.json` (H1-B) recorded:

| units | identity + change detection p50 |
|---|---|
| 100 | 97.9 ms |
| 250 | 1.20 s |
| 500 | 3.02 s |
| 750 | 6.01 s |
| 1000 | 10.48 s |
| 10000 | **`MemoryError`** |

and separately recorded that the *downstream* selective recompiler, given a
dirty set, is 3.62x (1k) to 4.31x (10k) cheaper than a full rebuild at a ~1%
planned-rebuild fraction.

**These are two different stages and must never be reported as one number.**
The selective-recompilation saving is real and measured; it is measured
*downstream of* the identity stage, and the identity stage is the bottleneck.

## 2. Root cause, read off the code

`akc_cir.identity.assign_one_to_one` (pre-change) built a full
`len(incoming) x len(previous)` matrix in which **every cell held a
`(float, dict, dict)` triple** — the score plus its per-signal breakdown and
per-signal missing reasons — and then ran a Hungarian assignment over a square
padded to `max(N, M)`.

Two independent costs, and conflating them was the first mistake to avoid:

- **Memory** — `O(N*M)` triples. At 10,000 x 10,000 that is 10^8 cells each
  holding two dictionaries. This, not the arithmetic, is what raised
  `MemoryError`.
- **Time** — `O(N*M)` pair scorings plus an `O(max(N,M)**3)` pure-Python
  Hungarian.

`generate_candidates(window=24)` — the §N15.1 restriction the masterplan
requires, *"전 workspace global all-pairs 비교 금지"* — existed in the module and
**`assign_one_to_one` never called it**. The documented constraint and the
executed code disagreed. That is the finding.

## 3. The two changes, deliberately separated

**Change 1 — exact, unconditional.** Hold the score matrix as bare floats and
recompute `score_pair` for the one column each row is assigned. Same pure
function, same inputs, same decisions; strictly less memory. This is not a
policy and has no flag: it applies to `LEGACY`.

**Change 2 — `MatchingPolicy.BLOCKED`, shadow only.** Invert `previous` on
path root / explicit identifier / anchor, take each incoming unit's candidate
columns by lookup, split the resulting sparse bipartite graph into connected
components, and run the Hungarian assignment per component. Default stays
`LEGACY`. `BLOCKED` is promoted only on the evidence this protocol defines.

`BLOCKED` reproduces `generate_candidates`' `keep` predicate exactly and
**deliberately omits its `window=24` truncation**. Truncation is a second,
independently lossy step; folding it in would make any divergence
unattributable.

## 4. The per-row lemma, and precisely what it does not cover

`structural_path` is always *present* — `_path_agreement` returns a float, never
`None` — so a pruned candidate scores a hard 0.0 on a 0.20 weight while the rest
renormalise over available weight. Maximising over which other signals are
present, all at 1.0, gives `(1.00 - 0.20) / 1.00 = 0.80`; dropping any signal
lowers numerator and denominator by the same weight and so lowers the ratio.
**0.80 is the supremum for any pruned candidate.**

Therefore, for a fixed row:

- `0.80 < MERGE_THRESHOLD (0.92)` — a pruned candidate can never itself merge.
- `0.80 < MERGE_THRESHOLD - _TIE_BAND (0.87)` — a pruned candidate can never be
  the runner-up that fires the tie guard on a pair that would otherwise merge.

So pruning **cannot turn AMBIGUOUS or NEW into MATCHED for a given row.**

It does **not** establish whole-assignment equivalence. The matching is global:
dropping an edge can free a column that another row then takes, and that row's
outcome can change. This residual is **measured, not assumed**. Any claim of
equivalence in the paper or the patent cites §6's measurement, never §4's lemma
alone.

## 5. Falsification arm — mandatory

A zero is worthless until something makes it non-zero. The equivalence sweep
includes a `duplicate_text_decoy` topology in which a unit's text is duplicated
verbatim under a **different path root**, so the decoy is exactly the kind of
candidate the index prunes. If the harness reports no divergence anywhere
*including* this cell, the harness is presumed broken until a deliberately
weakened index is shown to produce divergence.

## 6. Pre-registered criteria — frozen before looking

Decisions are compared element-wise on the tuple
`(match, logical_id, relation, sorted(candidates))`. Score floats are compared
separately and are not part of the equivalence criterion.

A divergence is classified:

- **FAIL_OPEN** — `LEGACY` was `AMBIGUOUS` or `NEW` and `BLOCKED` is `MATCHED`,
  or the two are `MATCHED` onto *different* `logical_id`s. A wrong merge
  rewrites history undetectably; invariant 10 says this is the expensive error.
- **FAIL_CLOSED** — `LEGACY` was `MATCHED` and `BLOCKED` is `AMBIGUOUS`/`NEW`.
  Costs a rebuild; visible; not a correctness violation.
- **OTHER** — any divergence that is neither.

**Primary criterion:** `FAIL_OPEN == 0` across every cell.

**Secondary, reported not gated:** `FAIL_CLOSED` count, and the scaling table.

**Promotion rule, frozen now:** `BLOCKED` may become the default **only** if
`FAIL_OPEN == 0` *and* `FAIL_CLOSED == 0`. `FAIL_OPEN == 0` with
`FAIL_CLOSED > 0` keeps `BLOCKED` a shadow policy and is reported as a
false-split cost, not waived. `FAIL_OPEN > 0` fails the change outright.

No threshold in this file is widened after a result is seen. A new statistic may
be added as a *measurement* and may become a criterion only in a later protocol.

## 7. Scaling measurement

`LEGACY` and `BLOCKED` timed on the same generated version pairs at
100 / 250 / 500 / 750 / 1000 units, and `BLOCKED` alone additionally at
2500 / 5000 / 10000. `LEGACY` at 10000 is expected to remain unrunnable and its
failure is recorded, not hidden. Reported per scale: p50, p95, mean over
trials, and `tracemalloc` peak. Wall-clock is CPU-local and carries no GPU cost;
`external_gpu_cost_usd` is 0.0.

The corpus is **controlled and generated**, not a real document corpus. Every
number produced here is labelled controlled and may not be presented as
real-corpus evidence.

## Amendment 1 — 2026-08-19, falsification arm replaced

**Recorded before any §6 equivalence result was accepted, and after the first
falsification run returned zero.**

§5 as frozen named one weakening: reduce the candidate index to the path root
only, and expect divergence on `shared_identifier`. That run returned **zero
divergent decisions**, and §5 says a zero there means the harness is presumed
broken.

Tracing it rather than assuming a generator artifact: the weakening cannot
separate *by construction*. In `shared_identifier` the correct candidate shares
the incoming unit's path root as well as its identifier, so removing the
identifier and anchor unions removes only candidates that were never going to
win the assignment. The arm tested nothing.

This is a defect in the arm, not a result. It is corrected here rather than
silently: the original run is retained in the receipt as
`identifier_and_anchor_union_removed` with `separates: false`, and it is
**not** treated as evidence that pruning is safe.

The arm that carries the claim is now `path_root_bucket_removed`, run on
`stable`: no unit there shares an identifier or an anchor with any candidate,
so removing the path-root bucket empties every candidate set and every decision
must move. If that arm returns zero, the comparator is broken and no §6 zero
may be reported.

No equivalence threshold, criterion or classification in §6 is changed by this
amendment. The promotion rule is unchanged.

## Amendment 2 — 2026-08-19, repeat count and probe bound

Recorded before the scaling receipt was accepted. **No equivalence criterion,
classification or promotion rule is touched.**

§7 asked for `LEGACY` and `BLOCKED` timed at 100/250/500/750/1000. A first
attempt was stopped after ~340 CPU-seconds without producing a receipt: at 750
and 1000 units `LEGACY` is `O(N*M)` pair scorings plus an `O(max(N,M)**3)`
pure-Python Hungarian, and five repeats plus a warm-up plus a `tracemalloc` pass
at each of those scales does not terminate in a useful time.

Two bounded deviations, chosen so that scale coverage is kept and only
precision is spent:

- `LEGACY` repeat count drops from 5 to **1** at 750 and 1000 units. p50/p95
  over a single sample are that sample; the receipt records `legacy_trials` so
  the weaker basis is visible rather than implied. `BLOCKED` keeps 5 everywhere.
- The `LEGACY` ceiling probe attempts **1500 and 2500 only**, under a
  wall-clock budget, and cites H1-B's already-measured 10,000-unit `MemoryError`
  rather than re-running for hours to reconfirm it. A step not attempted is
  recorded as `not_attempted` with its reason and is never reported as a pass.

The equivalence phase is unaffected and is run to its own receipt so that the
correctness gate does not depend on the timing phase completing.

## Amendment 3 — 2026-08-19, provenance re-run after a formatting change

**No criterion, classification or promotion rule is touched.**

`shadow-equivalence-2026-08-19.json` pins `identity_module_sha256`. After it was
written, `identity.py` was reformatted by `ruff --fix` (import ordering and a
`noqa` directive). The reproducibility manifest detected the resulting
`DRIFTED` pin — which is what it is for — and a receipt whose pinned module no
longer hashes to live source cannot be cited as describing current code.

Two options existed and only one is legitimate. Editing the receipt's hash to
match is forbidden: it would assert a measurement that was never made against
that code. So the equivalence phase is **re-executed against the current
module**, at the same seed, same cases, same units, to
`shadow-equivalence-rerun-pinned-2026-08-19.json`.

This is a re-execution for provenance, not a second attempt at an endpoint. Two
things make that distinction real here:

- The harness is deterministic and the seed is unchanged, so the re-run is a
  repetition rather than a fresh draw. If the totals move, the formatting change
  was **not** behaviour-preserving, and that is itself the finding — it would be
  reported, not smoothed over.
- H1-E is not a one-shot sealed endpoint. The one-shot endpoint in this
  programme is the Family B fresh-seed holdout, which was verified by hash this
  session and deliberately **not** re-executed.

`shadow-equivalence-2026-08-19.json` is retained unedited and superseded. The
claim–evidence matrix cites whichever receipt pins live code.

## 1. Where the build runs

### (1) Temporary RunPod builder pod — recommended

`buildah`/`podman` build an OCI image the same way regardless of whether a
GPU is attached: a Dockerfile with `FROM nvidia/cuda:...` or
`FROM vllm/vllm-openai:...` just unpacks and layers filesystem content. The
GPU is a runtime dependency of the *container*, not of the *build tool* — a
CUDA-runtime image builds correctly on a plain CPU pod, and only needs a GPU
the moment something inside it calls `cuInit`. This mirrors
`infra/runpod/v6/builder_pod.py`'s own framing ("Builder Pods are
intentionally not benchmark runtimes"), except that module still requests a
GPU pod (its `_ALLOWED_GPU` set is A40/A6000/L40S/4090) where this campaign's
builds do not need one at all.

Verified live against the RunPod catalog (`list-cpu-types`, 2026-09-03):

| CPU flavor | secure $/vCPU-hr | RAM/vCPU |
|---|---:|---:|
| `cpu3g` General Purpose | $0.04 | 4 GB |
| `cpu5g` General Purpose | $0.046 | 4 GB |
| `cpu3c` Compute-Optimized | $0.03 | 2 GB |

An 8-vCPU `cpu3g` secure pod costs **$0.32/hour** — recommended baseline
(32 GB RAM is comfortable headroom for `buildah bud` unpacking a multi-GB
base layer). `RTX 4090` community pricing was cross-checked at the same time
and reads **$0.34/hour**, exactly matching the masterplan's §13.2 figure —
the catalog is live and consistent with the plan's own numbers.

Disk: `build_plan.json`'s `builder_pod.disk_gb` is
`max(40, estimated_image_gb * 2.5)` per model, to hold the pulled base
layers, the new appended layer, and the pushed blobs concurrently without
needing to `buildah rmi` between steps. The one model that actually reaches
the "100-150 GB" band this lane brief warns about is `hpd_parsing`
(estimated 140 GB *because its official base image already ships the model
weights* — see §4) → **350 GB** builder-pod disk. Every other model's disk
need is 40-60 GB.

**Credential delivery**: the registry push token is delivered **over SSH**,
written into the pod's environment by nothing at all. `builder_pod.py`'s own
pattern already makes this point implicitly (pod `env` only ever carries a
`PUBLIC_KEY` and a role marker); ARENA_CONTRACT §5 makes it explicit for pod
env in general ("Never `HF_TOKEN`... pod env is readable through the
provider API"). The same logic applies to a GHCR push token a fortiori: pod
env is visible to anyone who can call `GET /v2/pods/{id}` with the campaign's
API key, and a builder pod's whole job is to hold a write-capable registry
credential. `build_on_pod.sh` (generated by `builder_pod_plan.py`) reads
`$ARENA_REGISTRY_TOKEN` from the interactive SSH session's environment,
`buildah login --password-stdin` once, then `unset`s it — the token is never
written to a file on the pod's disk and never appears in `dockerStartCmd`.

Cost, all 11 builds sequentially on one such pod (`build_plan.json` sums to
213 estimated minutes = 3.55 hours): **3.55 h × $0.32/h ≈ $1.14**, plus the
pod's minimum billing granularity and any idle time between builds. Even at
3x that for pull/push bandwidth and retries, image building is a rounding
error against the campaign's $250 target budget — the real spend is GPU
canary + Full Run time, not this step.

### (2) GHCR as the registry — verified reachable, scope confirmed

`registry_target` in `build_plan.json` is
`ghcr.io/0ssol1620-byte/tavonel-arena/<model_key>`. Verified live
(`gh api -i user`, this session, 2026-09-03): the configured token's
`X-OAuth-Scopes` header includes `write:packages` (classic PAT scopes do not
separately enumerate `read:packages`, but a classic token with
`write:packages` conventionally carries package-read too — `registry_check.py`
reports this distinction rather than assuming it). `build/registry_check.py`
is the read-only script that reproduces this check plus an anonymous GET of
every target manifest; running it now:

```
== GitHub token scopes (gh api -i user; scopes only, never the token) ==
  scopes: ... write:packages ...
  write:packages present (implies package read/write on classic PATs)

== Target manifests (ghcr.io, anonymous GET) ==
  <model_key>   inconclusive (anonymous_token_exchange: token endpoint returned 403)
  ... (all 11)
```

**Important, concrete finding**: every target manifest check comes back
*inconclusive*, not 404. GHCR's anonymous-pull token endpoint answers `403
DENIED` for a repository path that has never been pushed to at all (as
opposed to Docker Hub / a Harbor-based registry, which answer with a token
that then gets a `404` on the manifest GET — verified by the same code path
against `ccr-2vdh3abv-pub.cnc.bj.baidubce.com` for `paddleocr-vl`, which
*does* return 404 after a granted anonymous token). This means
`registry_check.py`'s "not yet pushed" signal for GHCR specifically will not
distinguish "namespace has never been created" from "namespace is private"
until after the first push, when the package's visibility is set to public
in the GHCR UI/API. Record that as a manual step in the promotion runbook,
not an automated check.

### (3) Cloudflare R2 as an OCI registry — **not supported**

R2 is an S3-compatible **object store**; it speaks the S3 API (`GET`/`PUT`
object, presigned URLs — exactly how ARENA_CONTRACT §5 already uses it, for
the worker bundle and runtime bundles). It does not implement the OCI
Distribution Specification (no `/v2/<name>/manifests/<ref>`,
`/v2/<name>/blobs/<digest>`, tag-listing, or content-addressable blob
endpoints), so nothing that pulls an image with `docker`/`buildah`/`podman`
or the Kubernetes/containerd pull path can point at it as a `FROM` source or
a push target. Cloudflare's own product positions R2 as a place to *store*
artifacts (backups, static assets, and — relevant here — the worker bundle
tarball this campaign already puts there) that get fetched by presigned URL,
never as a registry a container runtime resolves references against. Nothing
in this build plan treats R2 as anything but blob transport, matching how
lane B1's `arena/provider/r2.py` is scoped in ARENA_CONTRACT §5.

### (4) "Bootstrap-on-official-image" for canaries

Every `runtimes/<model_key>/bootstrap.sh` already exists (written by
lanes C1-C3) as the canary-only escape hatch MP §15.1 explicitly carves out:
start from the *official* upstream image (`vllm/vllm-openai`, PaddleOCR-VL,
HPD-Parsing, MinerU's own base), download the worker bundle from
`$ARENA_BUNDLE_URL` (a presigned R2 URL), install the campaign's pinned
package versions on top, and pull weights straight into
`/workspace/arena/weights/<model_key>`. Its exact limits, restated from the
masterplan and the contract:

- **canary-only, never Full Run.** MP §15.1 forbids `pip install` during the
  Full Run in the strongest terms ("금지: pod start → pip install 수십 개 →
  ... → idle GPU billing"); a bootstrap pod pays that install-and-download
  cost on every single pod start, which is exactly the failure mode §15.1
  exists to prevent at scale (5,132 pages × up to 12 models).
  `runtime_mode_allowed` in every `runtime.json` reflects this: it is either
  `["baked"]` or `["baked", "bootstrap"]`, never `["bootstrap"]` alone.
- **`inference_job_id` marks it.** ARENA_CONTRACT §2 makes bootstrap mode
  visible in the identity itself: `runtime_image_digest` becomes the string
  `"bootstrap:<runtime_bundle_sha256>"` rather than a real image digest, so a
  bootstrap-mode job can never be mistaken for a baked one downstream.
- **No install-version guarantee across pod restarts.** A baked image freezes
  `pip freeze`/`apt` state at build time (MP §38 Runtime Provenance); a
  bootstrap pod re-resolves whatever `pip install` picks up each time it
  starts (barring pinned versions, which the bootstrap scripts do specify,
  but an upstream index outage or a yanked release is a live failure mode a
  baked image does not have).
- **`runtime_provenance`, not skipped.** `/v1/provenance` (ARENA_CONTRACT §4)
  still reports versions/cuda/torch/etc regardless of runtime_mode — a
  bootstrap canary's provenance is real evidence, just evidence gathered
  fresh every pod start rather than frozen once at build time.

## 2. Recommended sequence

```
1. canary in bootstrap mode         (existing bootstrap.sh, official base image,
                                      presigned worker-bundle URL, no baked image
                                      needed yet)
        │  10-20 pages per model (MP §17), GT-blind deterministic selection,
        │  canary passes on runtime correctness only
        ▼
2. freeze the proven pins           (pip freeze / apt snapshot the bootstrap pod
                                      actually ran with, captured in its
                                      /v1/provenance response — this becomes the
                                      exact version set the Dockerfile bakes,
                                      never a re-guessed "latest compatible")
        ▼
3. bake                             (builder pod §1 above: buildah bud + push to
                                      GHCR, immutable digest, image_receipt.schema.json)
        ▼
4. re-canary on the baked image      (10 pages, same deterministic selection,
   (10 pages)                        confirms the baked image reproduces the
                                      bootstrap canary's behaviour byte-for-byte
                                      on raw_output_sha256 where determinism is
                                      expected, and that runtime_image_digest is
                                      now a real digest, not "bootstrap:...")
        ▼
5. Full Run                         (only after step 4 PASS; controller's own
                                      gate already refuses `run --model X
                                      --execute` for a model whose canary hasn't
                                      passed — README.md "Paid-action gate")
```

This sequence exists because a bootstrap canary answers "does this model's
official inference path even work on our staged PNGs, with our prompt, at
our resolution" cheaply (no image build, no push, minutes of GPU time) before
paying to build and push an 11-140GB image; baking before any canary risks
building an image around a config that turns out to be wrong on page 1.

### Concrete risks found while generating this plan (not hypothetical)

- **`paddleocr_vl_1_6`'s pinned tag does not exist upstream.**
  `runtime.json.base_image` names
  `.../paddlepaddle/paddleocr-vl:paddleocr3.7-nvidia-gpu`. An anonymous
  `tags/list` against that exact CCR/Harbor repository (read-only, this
  session, 2026-09-03) returns tags only up to the `paddleocr3.6-*` family
  plus a separate `latest*` family — no `3.7` tag of any kind exists yet.
  `runtimes/paddleocr_vl_1_6/Dockerfile`'s `FROM` will fail to pull as
  written. This is lane C1's file to fix, not lane F's to edit; recorded here
  because it blocks step 3 (bake) for this model regardless of anything in
  `build/`.
- **Two of eleven `base_image` values are not digest-pinned**
  (`paddleocr_vl_1_6`, `hpd_parsing`), which fails
  `arena/core/schemas/runtime.schema.json`'s own `base_image` pattern
  (`^[^\s@]+@sha256:...$`). `hpd_parsing`'s floating `-offline` tag *does*
  currently resolve (confirmed live), but a floating tag can be repointed by
  the vendor at any time between build and canary with no signal to this
  campaign.
- **GHCR anonymous-pull denial ≠ "not pushed" (see §1.2 above)** — the
  promotion runbook needs a manual "did I actually create+publicize the
  package" step, not just `registry_check.py`'s automated read.
- **Every image-size/build-time number here is unmeasured.** The first real
  build of each `model_key` must regenerate `build_plan.json` with observed
  values (`generate_build_plan.py` reads `runtime.json` fresh each run; only
  `estimates.py`'s numbers need hand-updating once real data exists).

## 4. What this build plan deliberately does not do

- It does not create a pod, push an image, or spend a dollar. Every producer
  in `build/` is a generator or a read-only check.
- It does not download model weights (forbidden this phase, ARENA_CONTRACT
  §9 — "no lane downloads model weights in this phase").
- It does not touch `runtimes/<model_key>/*` (owned by lanes C1-C3) even
  where this plan found a concrete defect in one; see
  `INTERFACE_CHANGES_PROPOSED` in the lane report for how those are surfaced
  instead.
- It does not decide GPU pool assignment for inference pods
  (`gpu_pool_priority` in `runtime.json`, owned by C1-C3, consumed by B1) —
  `builder_pod.disk_gb`/`gpu_required: false` here describes only the
  *build*-time pod, never the eventual inference pod.

### 5.2 Task 2 — base-image config inspection (entrypoint/cmd/python)

`generate_build_plan.py` now calls a new read-only module,
`build/image_config_inspect.py`, for every model_key: it anonymously fetches
the manifest at the *already-resolved* digest (preferring the exact digest
`build_plan.json` recorded over the floating tag), follows a multi-arch
index to its `linux/amd64` sub-manifest when present, fetches the image
config blob, and extracts `Config.Entrypoint` / `Config.Cmd`. It never
executes the image, so `python_on_path` is a **best-effort, non-fabricated**
read of the config's declared `Env` (a `PYTHON_VERSION=` variable when
present, else a known venv/conda directory if it appears on `PATH`) — a
candidate signal, not a verified filesystem fact. Every field is `null` and
`resolved: false` on any failure (non-200, refused anonymous config read,
no `linux/amd64` manifest in an index), with the exact HTTP status recorded
in `detail`; nothing is guessed.

Live run, 2026-09-03, all 11 base images (`resolved: true` for every one —
every upstream registry, including both Baidu CCR/Harbor mirrors, granted
anonymous config reads):

| mineru_pipeline | `["vllm", "serve"]` | `null` |

**Why this matters for D2**: every `vllm/vllm-openai`-based official image
(8 of 11) already sets `ENTRYPOINT ["vllm", "serve"]` — exactly the
ENTRYPOINT that bootstrap mode's `dockerEntrypoint: ["/bin/bash", "-c"]`
(REST v1) must override for the worker bundle to run at all; on REST v2 this
would be impossible (§11 D2 — v2's `args` only appends to an existing
ENTRYPOINT, it cannot replace one), which is the concrete evidence behind
D2's "bootstrap on `vllm/vllm-openai` and similar images is impossible
through v2" finding. `deepseek_ocr2` and `unlimited_ocr` (PyTorch/CUDA base
images) already run `nvidia_entrypoint.sh`, a wrapper that execs its `CMD`
after some NVIDIA-specific setup — bootstrap mode replaces that wrapper
entirely rather than composing with it, so the bootstrap script cannot
assume any NVIDIA-entrypoint side effect ran. `paddleocr_vl_1_6` and
`hpd_parsing` (the two Baidu CCR / Harbor-hosted vendor images) each already
launch their own long-running server process by `CMD`/`ENTRYPOINT` — the
vendor's serving stack, not the arena worker — which bootstrap mode must
likewise override, and which C1's `runtimes/{paddleocr_vl_1_6,hpd_parsing}`
bootstrap/entrypoint scripts need to start deliberately (per 11.3 point 5)
rather than relying on the base image's own launch behavior.

`python_on_path` came back non-null for all 11 models on this run:
`paddleocr_vl_1_6` is the one image whose config declares
`PYTHON_VERSION=3.10.16` directly (the strong signal); the other 10 (every
`vllm/vllm-openai`-based image plus `deepseek_ocr2`/`unlimited_ocr`) carried
no `PYTHON_VERSION` var, so the fallback fired instead — a known venv/conda
directory (`/opt/conda/bin` or `/usr/local/bin`) appearing on the config's
`PATH`, recorded as a *candidate*, explicitly labeled unverified since
nothing here executes the image to confirm a `python3` binary actually
lives there. Full per-model detail (including the raw `PATH` string each
finding was read from) is in `build/build_plan.json`'s
`models.<key>.base_image_config`.

Tests: `tests/build/test_image_config_inspect.py` (mocked-transport —
single-arch manifest, multi-arch index → `linux/amd64` selection, 401 →
anonymous-token retry, a registry refusing the anonymous config read, a

### 5.3 Task 3 — D12 storage analysis: GHCR quota, public alternative, network-volume weights

**Source 1** (read live, 2026-09-03):
<https://docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-packages>
— GitHub's own Packages billing page.

The generic **GitHub Packages** free storage/bandwidth quota by plan
(applies to non-container package types — npm, Maven, NuGet, etc.):

| Plan | Storage | Data transfer / month |
|---|---:|---:|
| GitHub Free | 500 MB | 1 GB |
| GitHub Pro | 2 GB | 10 GB |
| GitHub Team | 2 GB | 10 GB |
| GitHub Enterprise Cloud | 50 GB | 100 GB |

**But this campaign uses the Container registry (GHCR), which is a
separate line item on the same page and is explicitly exempt right now:**

> "Billing for container image storage: Container image storage and
> bandwidth for the Container registry is currently free. If you use
> Container registry, you'll be informed at least one month in advance of
> any change to this policy."

So the literal answer to "what does 11 private GHCR images cost in
storage/bandwidth" is **$0 today**, regardless of the Free/Pro/Team/
Enterprise table above (that table is for *non-container* package types and
does not gate `ghcr.io/.../<model_key>` image pushes or pulls) — but it is a
policy GitHub can change with 30 days' notice, not a contractual guarantee,
and this campaign's 11-image, up to ~293 GB estimated footprint (§3) would
land well outside even the Enterprise Cloud non-container quota if the
container exemption were ever withdrawn. `write:packages` scope was already
confirmed present on the configured token (§1.2); nothing about the free
container-storage policy changes that push mechanics.

**Public-package alternative**: also $0 (container storage is free
regardless of visibility), and additionally removes §1.2's "inconclusive
anonymous-pull" ambiguity — a public package answers a plain anonymous GET
directly. The cost is not monetary: a public GHCR package exposes the arena
worker code baked into the image (`arena/` package, `runtimes/<key>/`
scripts) and, for every `weights_strategy: baked` model (10 of 11 — see
§3's table), the model weights baked into that image layer. Per CLAUDE.md's
FTO rules ("readable is not reusable" / "code, model weights, dataset and
hosted-API terms are four separate licences"), publishing a package makes
its *bytes* trivially copyable even though that grants no one a reuse right
— for a weight whose license terms restrict redistribution rather than mere
use, baking it into a publicly-pullable image is a live distribution
question the founder decides, not an engineering default.

### 5.4 Task 4 — D2: bootstrap canary path is REST v1

The canary-only bootstrap path (§1(4) above) now runs through RunPod
**REST v1** (`https://rest.runpod.io/v1`, deprecated but live — verified in
ARENA_CONTRACT D2 with the campaign key), not v2: `PodCreateInput` accepts
`dockerEntrypoint: ["/bin/bash", "-c"]` and `dockerStartCmd: [<script>]`,
which v2's `CreatePodRequest` cannot express (v2's `args` only appends to
whatever ENTRYPOINT the base image already has — see §5.2's finding that 8
of 11 official images already set `ENTRYPOINT ["vllm", "serve"]`, which v2
could never replace). §1's recommended sequence step 1 ("canary in
bootstrap mode") and step 4 ("re-canary on the baked image") are therefore
not symmetric on API version: step 1's bootstrap pod is created through
REST v1 with `dockerEntrypoint`/`dockerStartCmd`; step 4's baked-image
re-canary pod is created through REST v2 with no `args` at all, per
ARENA_CONTRACT §11.3 point 6 ("Baked images ... are created through REST v2
with no `args`"). The pod ledger records `provider_api_version` (`"v1"` or
`"v2"`) per D2 so this distinction is visible after the fact, not just in
this plan.

This campaign's own **builder pod** (§1(1) above, `cpu3g`, no GPU) was
already being planned as a v1-shaped resource before this decision existed
— `builder_pod_plan.py`'s `provider_request_dry_run()` already emits
`dockerEntrypoint: ["/bin/bash", "-c"]` and `dockerStartCmd: [<script>]`
as a single-element **list**, matching `PodCreateInput`'s v1 shape exactly.
No code change was needed there: the builder pod's `dockerStartCmd` was
never a bare string, so there is no v1/v2 start-command mismatch to fix in
`builder_pod_plan.py` for this pass. What *did* need documenting is that the
builder pod, being CPU-only and GPU-free, was never actually gated by D2's
"can v2 override an ENTRYPOINT" question in the first place (it boots a
plain Debian-family base with no vendor ENTRYPOINT to override) — it simply
happens to already be shaped the way D2 requires for the worker-bootstrap
pods, which is a coincidence of `builder_pod_plan.py`'s pre-existing design,
not a fix made in response to D2.

### G-A · 제품명 → **TAVONEL**

최초 결정 2026-08-07 (Structara → FOLYNTA).
**개정 2026-08-07 (FOLYNTA → TAVONEL).** 오너 판정.

**현재 정본**

```
제품명        TAVONEL
카테고리      The Knowledge Compiler
브랜드 서사    A traceable path from every source to knowledge.
```

**이름과 서사를 분리한다.** 이름은 기억성과 회사 정체성을 담고, "출처에서
지식으로 잇는 다리"라는 의미는 이름 안에 넣지 않고 서사가 담당한다. 이름이
의미를 직접 지시하지 않으므로 제품이 확장될 때 이름이 제품을 좁히지 않는다.

**개명 이력**

| | 클래스 | 에셋 | 디자인 시스템 |
| --- | --- | --- | --- |
| Structara (기준선 `main@7ac5098`) | `st-` | `STR-` | `design-system/ai-knowledge-compiler/` |
| FOLYNTA (`1414141`) | `fl-` | `FLY-` | `design-system/folynta/` |
| **TAVONEL (현재)** | **`tv-`** | **`TAV-`** | **`design-system/tavonel/`** |

두 개명 모두 시각 변경 0, revert 가능한 단일 커밋으로 유지했다.

**§4.2 브랜드 근거가 다시 소멸한다 — 중요하다.**

설계도 §4.2 는 대응면(FacingPages) 형태의 정당성을 "FOLYNTA = folio, 펼친
지면은 이 이름에서만 나온다"로 세웠다. TAVONEL 은 folio 파생이 아니므로 그
논거는 **없다.** §4.2 가 이 경우를 미리 적어 뒀다 — "G-A에 종속. folio 근거는
소멸하고 제품 사실로만 방어한다."

따라서 대응면은 이제 **제품 사실로만** 방어된다. §4.2 가 지목한 두 조건이
장식이 아니라 **성립 조건**이 된다:

```
① 좌측이 우리가 통제하지 않은 실제 문서 페이지다
② 스레드가 그 페이지의 실제 좌표에서 계산된다   ← §14.4 좌표 계약
③ 검증되지 않은 것은 우측에 도달하지 못한 채 남는다  ← §11.2 R3 흉터
```

①만으로는 Resend·Retool·Cursor 와 같은 화면이다. **②③이 없으면 대응면을
쓸 이유가 없다.** W4 의 G-E 좌표 계약과 W3 의 흉터 구현이 브랜드 필수 항목으로
승격된다 — 미루면 형태의 근거 자체가 사라진다.

**주의** — 상표 clearance 는 여전히 별개 트랙이며 **미완이다.** 결과가
부정적이면 개명을 다시 되돌려야 하므로 단일 커밋 원칙을 유지한다. 저장소가
2026-08-07 부로 공개 상태이므로 TAVONEL 사용 시점이 공개 기록으로 남는다.

### G-B · 서체 획득 → **Wanted Sans Variable (OFL) + 설계도 §7.2 B안**

결정일 2026-08-07.

```
서체        Wanted Sans Variable   OFL · 가변 · 라틴+한글 단일 소스
조달 비용    0
리드타임     0
```

**선정 근거**

- **Pretendard를 배제한 이유** — 라틴이 문자 그대로 Inter 파생이다(제작자가 Inter를 명시적으로 크레딧). 설계도 §7.1의 "Inter는 템플릿 신호" 논거가 한글에도 그대로 적용된다. 한국 시장의 사실상 기본값이라 "서체를 고르지 않았다"로 읽힌다.
- **Wanted Sans를 고른 이유** — OFL이면서 가변이고, 라틴과 한글을 한 곳에서 같이 그렸다(설계도 §7.2가 요구하는 획 두께·스트레스 정합이 설계 단계에서 이미 맞춰져 있다). 시장 기본값이 아니다.
- **SUIT 배제** — 가변이지만 2,668자 커버리지라 사용자 생성 콘텐츠에서 결자가 난다.
- **IBM Plex Sans KR 배제** — 라틴-한글 페어링은 가장 정교하나(한글 베이스라인 22%를 라틴 공존용으로 조정) **가변이 아니다.**
- **유료·커스텀 보류** — 커스텀은 라틴 $40–80k / 4–8개월 + 한글 9–24개월이다(Toss는 7개월에 2,350자만 확보). Sandoll 웹폰트는 **CDN 전용이라 self-host 요구와 자격 미달**이며 페이지 텍스트가 벤더로 전송된다. 영구·self-host·PV 과금이 확인된 유일한 벤더는 Typotheque다.

**§7.2 B안(Linear 우회로)** — 세 기법 중 **둘만 적용한다.** 2026-08-07 개정.

```
✓ 비정수 웨이트 축      400/500/600 금지. 510 / 560 / 570 / 590 사용
✓ 크기 의존 트래킹      Display −0.03em → 본문 0 으로 수렴. 단일 값 금지
✗ OpenType feature 전역 적용   적용하지 않는다
```

**세 번째를 뺀 이유.** B안은 **Inter 를 위한** 우회로다 — 스톡 서체를 스톡으로
안 읽히게 만드는 기법이고, §7.1 이 Inter 를 "템플릿 신호"로 지목했기 때문에
필요했다. Wanted Sans 는 스톡이 아니다. **서체를 고른 것만으로 그 목적은
달성된다.**

실제로 이 기법을 적용했다가 되돌렸다. 설계도가 예시로 든 태그(`cv01`·`ss03`)는
**Inter 의 태그**이고, OpenType 태그는 폰트마다 매핑이 다르다. Wanted Sans 에서는:

```
ss03   소문자 a → a.cv21   원 안에 닫힌 고리. 라틴 a 로 읽히지 않는다 (+107자)
ss01   j · t · Q → 대체자                                        (+86자)
cv01   j → 대체자
```

`a` 는 영문 최빈출 글자 축에 들어, 사이트 전체 문장의 질감이 다른 문자 체계처럼
바뀌었다. **오너가 육안으로 지적해 발견했다** — 자동 검사 어디에도 걸리지 않는
종류의 결함이다.

**확정 — 표준 조판 기능만 쓴다:** `kern` · `liga` · `clig` · `calt`.
스타일 세트를 넣으려면 **시안과 근거를 붙여 한 태그씩** 넣는다.
미사용 대체자는 서브셋에서 제거했다 (27.8KB → 25.1KB).

**서체 성격 확정** — Wanted Sans 는 기하학적 산세리프다. 소문자 `a`·`g` 가
1층 구조이고 보울이 원형이다(Futura·Poppins 계열). 휴머니스트 산세리프의 2층
`a` 와 다르며, 이는 결함이 아니라 이 서체의 설계다. **오너가 시안 비교 후
이대로 확정했다 (2026-08-07).**

**재검토 시점** — W6 종료 시. 그때 Typotheque 견적을 받아 교체 여부를 판단한다.

## 설계도 개정 사항

머지 이후 조사에서 드러난 오류다. 다음 설계도 개정 시 본문에 반영한다. **그 전까지는 이 절이 설계도보다 우선한다.**

### A-01 · §22 폰트 예산 ≤90KB는 한국어에서 달성 불가능

실측이다.

```
Pretendard Variable 전체            2.06 MB
KS X 1001 서브셋 (정적 1웨이트)      267 KB
동적 서브셋 청크 1개                 ~35 KB
  → 한국어 문장 하나가 5–15개 청크를 끌어온다
```

**교체 예산**

```
/en                    ≤ 60 KB      하드 예산. 라틴 가변 서브셋 1개
/ko 마케팅 첫 화면       ≤ 180 KB     빌드타임 서브셋 기준
/ko 제품 UI 첫 화면      ≤ 250 KB     unicode-range 청크 기준
/ko 정상 상태           ≤ 400 KB
```

### A-02 · 한글에 가변 축을 쓰면 예산이 두 배가 된다

```
음절당 바이트   정적 1웨이트 청크    ~70–100 B
              가변(wght) 청크     ~150–200 B
```

**결정** — **가변 축은 라틴에만 둔다.** 한글은 빌드타임에 `fonttools varLib.instancer`로 **정적 2웨이트(400 / 600)**를 뽑아 쓴다. §7.2 B안의 "비정수 웨이트 스톱"은 라틴 축에만 적용된다.

### A-03 · `next/font`는 `unicode-range`를 지원하지 않는다

2023-03부터 열려 있는 이슈다(vercel/next.js #47309). `declarations`로 우회 가능하나 그 호출이 만드는 **모든** `@font-face`에 동일하게 적용되어 청크별 지정이 불가능하다.

**결정**

```
라틴 서체    next/font/local 유지 (adjustFontFallback 이득이 있다)
한글 서체    src/app/ 의 전역 CSS 에 @font-face 직접 작성
```

### A-06 · §8.1 심볼 기하가 자체 합격 기준을 통과하지 못한다

설계도 §8.1 은 24×24 캔버스에 네 요소를 그리고 "**16px 에서 세 요소가 분리되어


두 획이 겹쳐 하나의 두꺼운 막대로 렌더되고, 그 안에 스레드가 묻혀 보이지 않는다.
16 · 20 · 24 · 32 · 64 · 128px 전부에서 그렇다.

**개정 — 스파인을 별도 획이 아니라 여백으로 둔다.** 요소가 정확히 셋(좌면 ·
우면 · 스레드)이 되어 §8.1 이 세라고 한 숫자와 맞고, 실제 folio 의 접힘과도
맞는다. 의미는 그대로다.

```

우면(Knowledge)  x 14.5–21.5, y 6.5–17.5  좌면보다 짧다
스레드           (9.5, 15.4) → (14.5, 12)  Δ5 : Δ3.4 = −34.2°
stroke           ≤20px 1.9 / >20px 1.6
```

전 크기 + 그레이스케일 블러(§25.4)에서 검증했다.

### A-07 · §7.2 B안의 OpenType 기법을 적용하지 않는다

### A-09 · §22 LCP 의 원인을 정정한다 — TTFB 가 아니다

2026-08-08 실측(프로덕션 빌드 · 390×844 · 4x CPU · 라이브 페이지의
PerformanceObserver):

```
TTFB                    13ms      (5회: 9–17ms)
스타일시트 완료           91ms      (5개 파일 47.5KB)
first paint            204ms
first contentful paint 808ms
LCP                    808ms      요소: <h1> — 이미지가 아니다
```

기존 기록은 "LCP 는 TTFB 가 지배한다 — nonce 때문에 force-dynamic 이다"였다.
**틀렸고, 비싼 방향으로 틀렸다.** 그 기록을 믿고 행동하면 보안 제품의 CSP 를
13ms 를 벌려고 약화시키게 된다. 실제로 이 문서를 읽고 그 작업을 시작할 뻔했다.

LCP 요소인 `<h1>` 은 27ms 시점의 서버 HTML 에 이미 있고, opacity 1, 애니메이션
없음, 폰트는 `display: swap` + 메트릭 매칭 폴백이다. 텍스트도 타이포그래피도
지연 원인이 아니다. 스타일시트가 준비된 91ms 와 h1 이 그려지는 808ms 사이의
약 700ms 는 **초기 JS 의 파싱·평가**다.

그러므로 미달 3건은 원인이 하나이고, 그 원인은 이미 예산표가 지목한 191KB —
레거시 마케팅 페이지와 클라이언트 AppShell — 이며 W2 / W7 이 통째로 교체한다.
히어로 포스터(390px 22.8KB AVIF)는 무관하다. LCP 요소조차 아니다.

정정 자체가 교훈이다. §22 가 선언이었을 때는 원인도 선언이었다. 측정 인프라가
생긴 뒤에도 **원인만은 추정으로 남아 한 웨이브를 잘못된 방향으로 보낼 뻔했다.**

```
① --paper-1 을 실제 종이에서 뽑고 지종·평량 기록      미착수 · 결정 필요
② 그레인을 CSS 노이즈로 (§15.3)                      미착수 · 승인 필요
③ 액센트에서 앰버·테라코타·에메랄드 제외              충족
④ eyebrow 를 "대문자 + 점 + 규칙선" 에서 바꾼다       미착수 · 승인 필요
```

**③ 은 충족됐다.** tokens.css 의 색상각 전수 확인:

```
브랜드 255°   evidence 210°   danger 25°
paper  84° (채도 0.006–0.012 — 거의 무채색)
review 70°  verified 165°  — 둘 다 액센트가 아니라 의미 상태색이다
```

액센트는 255° 하나이고 디텍터가 지목한 세 색 어디에도 해당하지 않는다.
`--review` 70° 는 앰버 대역이지만 "검토 필요" 상태를 뜻하는 관습색이고,
설계도의 요구는 *액센트에서* 제외하는 것이다. 따뜻한 크림 종이(84°)는
§5.2 가 "재질을 바꾸지는 않는다"고 명시적으로 유지하기로 한 것이다.

**① 은 지어낼 수 없다.** "근거 있는 실제 종이"를 기록하라는 항목인데, 실제로
고른 지종이 없는 상태에서 그럴듯한 이름과 평량을 적으면 그것이 정확히 §25.7 이
금지하는 날조다. 종이는 사람이 고른다.

**② · ④ 는 승인이 필요하다.** 둘 다 화면을 바꾸고, Hero 시안은 G-F 로 이미
승인됐다. 승인된 시안을 승인 없이 고치는 것은 §24.1 을 뒤집는 일이다.
④ 의 현행 eyebrow 는 "대문자 + 모노 + 트래킹 + 브랜드색"이다 — 디텍터가 지목한
장식 점과 뒤따르는 규칙선은 없으므로 조합 전체는 아니지만, 대문자 라벨이라는
축은 그대로다.

**남은 정적 시안(Navigation · Proof · Live Compile) 승인 없이 해당 웨이브에
착수하지 않는다** (§24.1). Hero 는 G-F 로 승인됐으므로 W2 착수 가능하다.

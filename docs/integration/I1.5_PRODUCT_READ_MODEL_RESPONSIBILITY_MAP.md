## What the matrix shows

- **12 of 15 capabilities** (discovery progress, entity graph, source
  provenance, authority, temporal applicability, predecessor world,
  semantic change, impact/dependency, ASK state, evidence trace, document
  status, multi-job/cross-collection) are things `ProductEvent`/
  `WorldProjection` handles that neither `event-reducer.ts` nor
  `v6/event-model.ts` handles at all — including one apparent name
  collision (`authority`) that turns out to be an unrelated concept on
  inspection. `proven`.
- I1 §14.3's gap — "no identified consumer requires the new convergence
  layer" — is closed: Product App's real, mounted `/app/world` route family
  reads `WorldProjection`'s world-semantic fields directly (currently
  fixture-only, not yet live-wired, but the routes/components/reducer are
  real and mounted, not hypothetical). This is a consumer that exists now,
  not a speculative future one. `observed`.
- Two weak counter-signals exist, neither strong enough to change the
  conclusion:
  - **`parser/recovery state`**: `WorldProjection.lanes` is `WRONG
    ABSTRACTION` — a narrative log reimplementing a lookup `event-reducer`
    already does better. This argues "don't reinvent," not "converge
    ownership."
  - **`replay/idempotency`**: independently implemented three times, with
    three different guarantee strengths (job plane: gap-buffered
    reassembly; collection plane: gap-count exposure only; world plane:
    silent drop). Each plane's sequence space is genuinely different (I2
    §5 already proved this), so this is not evidence for merging — it's
    evidence the three planes solve genuinely different problems at
    different granularities.

## Recommendation: **B — operational planes and world-semantic plane coexist**

`event-reducer.ts` and `v6/event-model.ts` are an **operational plane**:
per-job/per-collection processing state (page status, worker pools, cost,
gap/conflict counts) — the things an operator or a live-processing UI needs
to know *while work is happening*. `ProductEvent`/`WorldProjection` is a
**world-semantic plane**: entity identity, provenance, authority,
temporal state, change/impact, and answerable questions — the things a
knowledge consumer needs to know *about the compiled result*, independent
of which job or collection produced it.

- **Not A (redundant, remove/reduce)**: no matrix cell supports this — every
  capability `ProductEvent` owns is `ABSENT` in both other consumers.
- **Not C (converge some responsibility)**: the two counter-signals above
  are real but don't rise to "some existing-reducer responsibility should
  move under `ProductEvent`" — if anything they argue the opposite
  (`WorldProjection` should stop reinventing `parser/recovery state`, not
  absorb it).
- **Not D (too broad, decompose)**: `product-event.ts`'s own union is
  already organized into clear thematic groups (discover / route / world /
  truth / change / ask), and none of the 12 world-semantic capabilities
  above is unused or redundant with another — no evidence a narrower
  boundary would help.
- **B is supported directly**: 12/15 capability rows show clean separation
  of responsibility with zero overlap, and the "no real consumer identified"
  gap I1 flagged is now closed with a real, mounted consumer.

## Note on the name-collision pattern

`authority` (v6's verification tier vs. `ProductEvent`'s temporal-conflict
resolution) is the same failure mode I1 §7 already documented for
`page.route.selected.v1` (same event-type name, structurally different
payloads across planes). Worth naming explicitly here so nobody later
assumes shared vocabulary implies shared capability across these consumers
— it doesn't, in either case found so far.
